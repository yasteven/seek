# seek

A procedural macro that exposes typed Tokio MPSC senders and receivers over QUIC streams. Applications own their actors, state, and request/reply policies.

## How it Works

The `seek!` macro parses a comma-separated list of types. At the crate root or module context where it is invoked, it generates:

* `ServerKernel` and `ClientKernel` execution loops.
* A `ConnectionHandle` struct tracking state per active socket connection.
* Dedicated, type-safe `tokio::sync::mpsc` channels automatically named after your identifier variants (e.g., `from_dude_snively` and `to_dude_snively`).

## Important: Ambient Dependencies

Because the code generated by `seek!` expands directly inside your application context, your dependent crate's `Cargo.toml` must include the networking, serialization, and runtime dependencies that the generated code calls:

```toml
[dependencies]
# Alias the package so the examples can use seek::seek!
seek = { package = "see-k", version = "0.1.1" }
# Required by the generated macro runtime engines
quinn = "0.11"
rustls = { version = "0.23", features = ["ring"] }
rustls-pemfile = "2.1"
tokio = { version = "1.21", features = ["full"] }
serde = { version = "1", features = ["derive"] }
bincode = "1.3"
log = "0.4"

```

## Usage Example

### 1. Macro Declaration

Define your domain types, and let the macro generate your asynchronous kernels:

```rust
pub mod ksta 
{
  // Bring your tracking structs/enums into scope
  use super::{Snively, MadeBot, GotTtai, GotTick00, GotTick01};

  // This single invocation expands into the complete ClientKernel, ServerKernel,
  // and ConnectionHandle structs bound to these types.
  seek::seek! 
  {   
    Snively, 
    MadeBot, 
    GotTtai, 
    GotTick00, 
    GotTick01 
  }
}
```

### 2. Running the Generated Engine

Once the macro handles the heavy lifting, your code initializes endpoints and runs the loop. Here is an example setting up a QUIC backend server loop utilizing the generated infrastructure:

```rust
use std::sync::Arc;

async fn run_seek_server() -> Result<(), Box<dyn std::error::Error>> 
{
  // 1. Prepare standard transport configurations
  let certs = load_certs_from_pem()?;
  let key = load_private_key_from_pem()?;
  let mut server_config = quinn::ServerConfig::with_single_cert(certs, key)?;
  
  let mut transport_config = quinn::TransportConfig::default();
  transport_config.max_idle_timeout(None); // Keep connection alive indefinitely
  transport_config.keep_alive_interval(Some(tokio::time::Duration::from_secs(3600)));
  server_config.transport_config(Arc::new(transport_config));
  
  // 2. Bind the QUIC endpoint
  let endpoint = quinn::Endpoint::server(server_config, "0.0.0.0:4433".parse()?)?;
  
  // 3. Instantiate the macro-generated ServerKernel
  let (new_connection_sender, mut new_connection_receiver) = tokio::sync::mpsc::channel(256);
  let mut server_kernel = ksta::ServerKernel::new(endpoint, new_connection_sender);
  
  // 4. Spawn the runtime loop generated by the macro
  let (cancel_tx, cancel_rx) = tokio::sync::mpsc::channel::<()>(1);
  tokio::spawn
  ( async move 
    { if let Err(e) = server_kernel.run(cancel_rx).await 
      { log::error!("ServerKernel run loop encountered error: {:?}", e);
      }
    }
  );

  // 5. Handle connections and their type-safe MPSC channels
  while let Some(mut handle) = new_connection_receiver.recv().await 
  {
    log::info!("New connection handle created: ID {}", handle.c_id);
    
    // The macro automatically creates individual channels for each specified type!
    tokio::spawn
    ( async move 
      { loop 
        { tokio::select! 
          { // Type-safe stream generated by passing 'Snively' to the macro
            Some(snively_msg) = handle.from_dude_snively.recv() => 
            { log::info!("Received messages over QUIC chunk layer: {:?}", snively_msg);
            }
            // Type-safe stream generated by passing 'MadeBot' to the macro
            Some(bot_msg) = handle.from_dude_madebot.recv() => 
            { log::info!("Received data from bot: {:?}", bot_msg);
            }
          }
        }
      }
    );
  }
  Ok(())
}
```

## Transport fixes and compatibility (wire version 2)

The Rust API is unchanged: `seek!(Types...)`, the public kernel fields and
constructors, `ServerKernel::run(cancel_rx)`, `ClientKernel::run()`, and every
`ConnectionHandle` field keep their existing names and types. Receiving a value
is still `handle.from_dude_type.recv().await`; transmitting is still
`handle.to_dude_type.send(value).await`. There is no built-in request ID,
expected-reply table, application acknowledgement, retry, or application timeout.

**Update both ends together. Wire version 2 is incompatible with the original
chunk protocol.** A setup handshake verifies the wire version and ordered Rust
`type_name` identities before publishing either connection handle. Every data
stream has an explicit lane header read to its exact length. Peers must use the
same shared message types in the same order. Rust type names are not a schema:
changing fields or Serde behavior under an unchanged name is not automatically
detected. Keep shared message definitions synchronized. Without another trait or
an explicit application schema/version, Serde cannot provide a complete schema
fingerprint. No new trait requirement is imposed here.

Messages use a four-byte big-endian length and one bincode 1.x fixed-integer,
little-endian payload, capped at **64 MiB serialized per message**. Invalid complete
frames, trailing bytes, oversized lengths, and truncated frames close the affected
connection and set its existing `CancelInfo` status. This bounds wire buffers, not
arbitrary allocation or computation performed by custom `Deserialize` code.
There is no application-level chunk assembly; QUIC already segments stream bytes.

Each direction retains its existing 8,000-message MPSC capacity. Both client and
server now apply backpressure rather than discarding received messages when full.
A successful MPSC send means local enqueueing, not remote application processing.
Cancellation or connection failure can still discard in-flight messages. Closing
an unused channel direction closes that direction only; callers may destructure a
handle and keep just the receivers/senders they actually use.

TLS and protocol setup run concurrently, with at most 128 pending setup tasks per
kernel and a 30-second setup deadline. One failed or stalled peer cannot block
other accepts/dials or the server cancellation mailbox. Connection publication,
mailbox delivery, and stream writes remain cancellable. Data stream tasks are
supervised, failures reach `CancelInfo`, and closed endpoints exit instead of
spinning. Closing the client's dialing mailbox lets submitted attempts complete;
already published handles remain usable after `ClientKernel::run()` returns.
There are no automatic reconnects. Successful concurrent dials may be delivered
in completion order; their `c_id` still comes from request order.

Generated code uses Tokio `JoinSet` (Tokio 1.21 or later) and Quinn 0.11. The
regressions can be run with `cargo test --all-targets -- --nocapture`.
